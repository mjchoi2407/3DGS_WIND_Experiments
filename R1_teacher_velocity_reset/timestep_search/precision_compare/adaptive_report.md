# 적응 FP32/FP64 보조 풀이 비교

## 현재 상태

2026-09-13. FP64 참 잔차로 FP32 보조 풀이를 승인하거나 FP64 GMRES로 전환하는 후보를 구현·실행했다.
**혼합 정밀도의 가속 이득은 확인되지 않았다. 같은 보정 알고리즘의 FP64 대조군은 생성 시간이28–30% 짧았다.**
순방향·역방향 실행 각각4경로×10프레임을 완료했다. 순방향의3경로는 모든640단계의 독립 GPU 물리·기하 검산도 통과했다.
기본 솔버는 바꾸지 않았다. 이 결과는1/6초 개발 검증이며10초 안정성·다른 메시·학습 적격성·R1 채택을 뜻하지 않는다.
설정·manifest·원본 hash·검증 분모·상세 수치는 [선별 근거](adaptive_evidence.json)가 소유한다.

## 조건과 연산별 정밀도 선택

입력은 `artifacts/runs/sub_pc/20260912T223433Z-aca6fc4223714a02a9fe8afe7f4edeef/bend_001`의 동결 입력이다.
이번 계산은 메인컴 GTX1080Ti에서 순차 수행했다. 서브컴의 과거 생성 시간과 비교하지 않았다.
손수건·굽힘1/100·초기 평면/속도0·기존 바람/물성·60Hz·64substep·dt=1/3840초를 유지했다.
CPU 모델/초기 구조 준비는 공통 FP64다. 사용자 diagnostic 정책은 유지하며 수치 허용오차는 완화하지 않았다.

| 연산 | 이번 후보의 선택 | 근거와 검증 경계 |
| --- | --- | --- |

| HVP·질량 작용·현재 접선 행렬 조립 | FP64 | 참 잔차와 행렬 일치 검사의 원래 연산자 보존 |
| 공력·질량 초기 가속도 풀이 | FP64 | 작은 추가 범위의 비교를 위해 유지. 이 항목의 FP32 불가능성을 증명한 것은 아님 |

| 잔차·norm·Newton/line search·에너지 검산 | FP64 | 판정 자체의 오차와 내부 잘못된 수렴 방지 |
| FP64 전환 후 GMRES·직교화·내적 | FP64 | 기존 수렴·재시작·전처리 재사용 유지 |

FP64 유지는 이번 후보의 정확도 확보 선택이다. 모든 개별 연산에서 FP32가 수학적으로 불가능하다는 판정은 아니다.
기존 FP32/hi-lo의 기하 보정과 새 보조 풀이 변경을 한 후보에 혼합하지 않았다.

## 적응 정책과 대조군

- `reference_hilo`: 기존 FP64/hi-lo + GMRES.
- `fp64`: 기존 단일 FP64 + GMRES.
- `refine64`: 단일 FP64 상태, FP64 보조 풀이와 참 잔차 보정. 혼합 후보와 같은 알고리즘 대조.
- `adaptive32`: 단일 FP64 상태, FP32 보조 풀이와 FP64 참 잔차/갱신.

현재 형상의 보조 행렬은 기존 coloring으로 FP64에서 조립·검사한다. 혼합 후보는 값을 GPU에서 FP32로 변환해 분해한다.
Newton의 각 선형계에서 보조 풀이 → FP64 해 갱신 → 원래 FP64 HVP/질량으로 `b−Ax` 재계산을 수행한다.
목표는 기존 EW 적응 상대 허용오차(floor1e-10, cap1e-4)다. 보조 FP32 행렬로 계산한 잔차를 승인 근거로 쓰지 않는다.

본 비교의 보정 상한은4회다. 잔차가 직전의0.5배 미만으로 줄지 않거나 상한에 도달하면 같은 RHS에서 FP64 GMRES를 시작한다.
실패한 보정의 해·잔차·첫 보조 풀이 캐시는 넘기지 않는다. 유한하지 않은 물리 평가와 기존 치명적 실패는 유지한다.
한 행렬 세대에서 보정이 실패하면 다음 행렬 재구축까지 보정을 생략한다.
FP64 수치 분해는 새 행렬의 첫 전환 때만 수행하고 같은 세대에서는 재사용한다.
기존64 Newton 호출 간격 재구축과 current 우선, 채택 평가 재사용, 병렬 합산을 유지한다.

선형 반복 집계에는 보정 풀이도 포함한다. `adaptive_counts`가 보정 횟수·FP64 GMRES 횟수·재분해를 분리한다.
`adaptive_ratios`는 최근 보정 시도의 각 반복 잔차/초기 RHS norm이다. 실행하지 않은 뒤쪽 슬롯에는 과거 값이 남을 수 있어
마지막 배열 전체를 한 시도의 수렴 곡선으로 해석하지 않는다. 정밀한 분석에는 실제 보정 횟수와 함께 사용한다.

## 시간과 비용

각 칸은 동일10프레임의 생성·진단 버퍼 기록·프레임 동기화 시간이다.

| 경로 | 순방향 실행, 초 | 역방향 실행, 초 |
| --- | ---: | ---: |
| FP64/hi-lo | 14.456 | 12.029 |
| 기존 FP64 | 9.948 | 9.736 |
| FP64 보정 대조군 | **7.122** | **6.841** |
| 적응 FP32/FP64 | 9.733 | 10.131 |

FP64 보정 대조군의 기존 FP64 대비 시간 감소는28.4%,29.7%다.
혼합 후보는2.2% 짧거나4.1% 길어 일관된 가속을 확인하지 못했다.
GPU 클록·외부 화면 부하를 고정하지 않았으므로 두 실행의 차이로 작은 가속률을 주장하지 않는다.
계측 없는 본 실행과 별도 `profile` 실행을 구분하며 이전 최적화의 비동기 타이머와 비교하지 않는다.

전송·파일 저장·hash 시간은 본 표에서 제외한다. 순방향 FP64/대조군/혼합에서 각각0.544/0.504/0.427초,
역방향0.384/0.395/0.399초다. `setup_s`는 모델 생성 후 solver 준비 구간으로 모델 생성·프로세스 시작을 포함하지 않는다.
따라서 타이머 일부의 합을 완전한 end-to-end 시간으로 부르지 않는다. 독립 검산도 생성과 별도 측정했다.

순·역방향 모두 혼합 후보의1152회 선형계 중 FP32 보정 채택은1회뿐이다.
보정56회 후1151회는 FP64로 전환했으며, 행렬18세대 모두 FP64 재분해가 필요했다.
이 중1133회는 앞선 실패 때문에 FP32 시도를 생략했다. 상한2회의2프레임 smoke에서도128회 모두 전환했다.
FP64 보정 대조군은1152회 모두 GMRES 없이 통과했고 보정2911/2916회를 수행했다.

별도10프레임 GPU 내부 계측의 원인 분리는 다음과 같다. 시간은 marker·scheduling 비용을 포함하고,
서로 중첩된 inclusive 시간을 합산하지 않았다.

| 연산 | 기존 FP64 호출/초 | FP64 보정 호출/초 | 혼합 호출/초 |
| --- | ---: | ---: | ---: |
| cuDSS 풀이 전체(초기 가속도 포함) | 5194 / 5.062 | 3557 / 3.819 | 5242 / 5.753 |
| HVP 전체(행렬 조립 포함) | 9378 / 2.658 | 7741 / 2.546 | 9426 / 3.040 |
| 수치 분해 | 18 / 0.099 | 18 / 0.125 | 36 / 0.214 |

혼합의 FP32 보조 풀이56회 자체는0.044초였지만 대부분의 FP64 작업을 대체하지 못했다.
FP64 대조군의 이득은 보조 풀이·HVP 호출 감소에서 확인된다. 모든 반복을 더 정확히 해서 반복 수가 줄었다는 설명과 구분한다.
표의 호출 수는 계측 실행의 값이며, 반올림·분해 순서 차이로 비계측 실행과 소수 반복 차이가 있다.

## 정확도와 검증

- 순·역방향 각각4경로 모두640단계 완료, 경고0, 프레임 끝 CPU FP64/longdouble 독립 분석 오류0.
- 순방향의 FP64/FP64 보정/혼합 각각640단계, 총1920단계를 별도 FP64/hi-lo GPU 검산기로 검사했다.
  힘·위치 업데이트·에너지 장부·고정점·비유한·Bernstein 기하 상한 실패0이며 시간축·기준 궤적 대조도 통과했다.
- 모든 단계의 최대 힘 잔차/허용오차는 각각0.297865/0.297897/0.297805로1보다 작다.
  프레임 마지막 표본 최대값과 분모가 다르다.
- 순방향 FP64 보정의 기존 FP64 대비 최대 위치/속도 성분 차이는5.259e-13 m/9.216e-10 m/s다.
  혼합은1.038e-14 m/2.069e-11 m/s다. 혼합의 작은 차이는 거의 모두 FP64로 전환한 결과다.
- 모든 단계의 에너지 장부 차이는7e-21 J 미만, 위치 업데이트 오차는4.3e-19 m 미만이며
  strain 상한은약3.569e-5다. 에너지 장부 일치와 물리 에너지 잔차 자체를 구분한다.
- 실제 Warp CPU 판정/산술5개, 기존 정밀도9개·변형률4개 검사 통과.
- 실제 GPU 소형 선형계에서 zero RHS, FP32 채택, 새 RHS, 오래된 보조 행렬의 FP64 전환,
  실패 세대의 반복 생략, 재구축 후 FP32 재시도를 검증했다. CPU 조회 금지와 host copy 거부 검사도 통과했다.
- CUDA13.0 driver에서 조건부 body 사후 조회 API가 없어 Warp1.17의 생성 hook으로 body를 추적했다.
  각 step/frame graph와 조건부 본문·cuDSS 자식 graph에서 host copy/callback0을 확인했다.
  기존 검산 함수는 body 목록 없이 조건부 node를 허용하지 않는다.

전체 단계의 GPU 검산은 순방향3경로에만 수행했다. 역방향/계측 실행은 프레임 끝 독립 CPU 표본 분석이다.
다른 메시·긴 시간·더 큰 변형·접촉·저장 재개는 이번 검증 범위가 아니다. 기하 예외나 학습 발행 보류를 해제하지 않는다.

## 재현

아래는 새 경로에서4경로 준비·실행·분석을 수행한다. 기존 결과를 덮어쓰지 않는다.

```bash
bash experiments/R1_teacher_velocity_reset/timestep_search/run_precision_compare.sh \
  --suite adaptive --correction-budget 4 --frames 10 \
  --out experiments/artifacts/runs/teacher_precision_compare/adaptive_new
```

`--prepare-only`는 준비만, 같은 출력의 `--run-prepared`는 동결 실행, `--status-only`는 상태 확인이다.
새 출력에서 `--reverse-lanes`로 순서 대조, `--profile`로 별도 내부 계측을 수행한다.
Ctrl+C와 interrupted 비재개·확정 파일 보존 정책은 기존 비교 실행기를 따른다.

원본은 `artifacts/runs/teacher_precision_compare/` 아래 다음 run이다.

- `20260913_adaptive_budget4_v1`: 순방향 비교.
- `20260913_adaptive_budget4_reverse_v1`: 역방향 비교.
- `20260913_adaptive_profile_v1`: 별도 내부 계측.
- `20260913_adaptive_smoke_v3`: 상한2회2프레임 기능 확인.
- `20260913_adaptive_validation_v1`: 실제 GPU 분기·세대 검증.
- `20260913_adaptive_all_steps_audit_v1`: 순방향3경로 전체 단계 독립 검산.

실제 GPU 검증 스크립트는 `code/scripts/check_teacher_adaptive_precision_actual.py`와
`code/scripts/check_teacher_adaptive_trace_actual.py`다. 전자는 해당 run의 `runtime/adaptive32`,
후자는 `runtime/reference_hilo`를 `PYTHONPATH`로 사용한다. 같은 run의 native shim/library를
`LD_PRELOAD`/`CUDSS_LIBRARY_PATH`로 지정하며 `--out`은 새 경로여야 한다.

이번 결과에 따른 권장 후보는 별도 FP64 보정 경로다. 혼합 정밀도는 비용을 회수하지 못해 기본 채택하지 않는다.
공식 CUDA 문서를 웹에서 조회했으며 Git fetch·기존 동결 결과 수정·commit·push는 하지 않았다.
