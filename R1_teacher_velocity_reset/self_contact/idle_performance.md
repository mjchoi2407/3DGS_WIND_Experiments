# GPU 셀프 컬리전 유휴 조건 재측정

## 결론

2026-09-22 사용자가 다른 GPU 작업을 종료했다고 확인한 뒤, GTX1080Ti에서 새로 측정했다.
**실제 동결 초기v1 대비 v4는 같은 여섯 초기 프레임에서16.2~28.2% 단축**됐다.
여섯 중앙값 합은18.437→14.730초, 약20.1% 단축(1.25배 처리 속도)이다.
이는 여섯 표본의 합이지 연속 궤적이나 실제 FPS의 측정은 아니다.

같은 실행기에서 분리한 셀프컬리전 추가 비용은 **비접촉 첫 프레임에서+15.7~43.5%**였다.
기존 기록의2.58~7.57배 증가·3.34배 prefix 차이는 부하/실행기가 다른 과거 관측이며
순수 접촉 비용의 기준으로 사용하지 않는다. 사용자는 최초 버전 측정에도 GPU 부하가 있었을
가능성을 알렸다. 당시 결과를 삭제하거나 당시 부하량을 사후 확정하지 않고 이번 재측정과 분리한다.

마지막 v4 병렬화만의 추가 효과는 표본별로 단축/증가가 섞였으며 변동 범위와 비슷했다.
**전체 개선은 확인했지만 v4 병렬화가 v3 재사용 경로보다 일관되게 빠르다는 근거는 부족하다.**
측정만 수행했으며 물리식·허용오차·기본 스크립트·운영 경로는 바꾸지 않았다.
본 preload/calm/wind는 미실행이고 측정 프로세스와 자체 telemetry 기록은 종료했다.

## 측정 조건과 비교 분모

- 같은 GTX1080Ti·driver582.28·Warp1.17.0·cuDSS/native byte/hash, FP64 hi/lo Newmark.
- 실제 동결v1/v4의 세 씬 중력/최대풍 입력 전체 파일·물성·정책·외력 hash 일치 확인.
  같은 rest/속도0에서1프레임64단계,dt1/3840초를 계산했다. 최대풍도 preload 후 상태가 아닌 rest 시작이다.
- 각 경로 예열1회 후 같은 초기 raw 상태로 복원하여3회 측정했다. 준비/컴파일·CPU 읽기·파일 저장은
  제외하고 **GPU 계산+모든 substep의 독립 검산**을 잰다. GPU 실험끼리는 동시 실행하지 않았다.
- 통제된 실행기는 최적화 전 `old_on`, 재사용만 `reuse_on`, 최신 `new_on`, 동일 실행기 `matched_off`를
  매 반복 순서 회전해 비교했다. `old_on`은 현행 소스의 최적화 OFF이지 실제v1 전체 소스는 아니다.
  AABB 진단 카운터 지역 집계는 이 대조군 모두에 공통이며 수치 기준·정밀 기하 검사는 동일하다.
- 실제 동결v1/v4는 별도 프로세스에서 원래 코드를 수정하지 않고 실행했다. 조건마다 버전 실행 순서를
  교대했다. v1에는 정밀 기하v2가 없으므로 기하 정책이 동일하다는 주장은 하지 않는다.
  비교한 여섯 프레임은 양쪽의 기존 승인 기준을 모두 통과했고 상태도 대조했다.
- `matched_off`는 비교 범위 내 활성 접촉이 모든 평가에서0임을 계수기로 확인한 경우만 사용했다.
  기존 M1/M2·Gauss 실행기와의 비교나 실제 접촉 궤적의 OFF 비용 추정이 아니다.

## 실제 초기v1 → v4

초,3회 중앙값. 아래 수치는 모두 이번 유휴 확인 후 새로 측정한 값이다.

| 씬 | 구간 | 동결v1 | 동결v4 | 시간 단축 |
| --- | --- | ---: | ---: | ---: |
| 직사각형 | 중력 | 2.794 | 2.342 | 16.2% |
| 직사각형 | 최대풍 | 5.117 | 4.194 | 18.0% |
| 손수건 | 중력 | 2.283 | 1.641 | 28.2% |
| 손수건 | 최대풍 | 3.161 | 2.505 | 20.8% |
| 삼각 깃발 | 중력 | 1.996 | 1.614 | 19.1% |
| 삼각 깃발 | 최대풍 | 3.086 | 2.435 | 21.1% |

각 경로3표본의 `(최대−최소)/중앙값`은0.09~4.16%였다. 별도 프로세스 비교이며
실행 순서를 교대해도 모든 시간 변동 요인이 제거됐다는 통계적 증명은 아니다.
Raw 상태의 최대 차이는 hi 위치3.03e-17m, hi 속도4.69e-13m/s 이하다.
상태 대조 허용오차rtol1e-7/atol2e-9와 원래 GPU 승인 기준을 모두 유지했다.

## 같은 실행기에서 분리한 접촉 비용과 병렬화 효과

이 표의v4 시간은 앞 표와 다른 측정 묶음이다. 서로 다른 묶음의 분모를 섞지 않는다.

| 씬 | 구간 | 접촉 OFF | 최적화 전 ON | 재사용만 ON | v4 ON | v4의 OFF 대비 증가 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 직사각형 | 중력 | 1.788 | 2.889 | 2.343 | 2.330 | +30.3% |
| 직사각형 | 최대풍 | 3.665 | 5.115 | 4.411 | 4.242 | +15.7% |
| 손수건 | 중력 | 1.360 | 2.278 | 1.772 | 1.756 | +29.0% |
| 손수건 | 최대풍 | 2.067 | 3.348 | 2.670 | 2.611 | +26.3% |
| 삼각 깃발 | 중력 | 1.252 | 2.175 | 1.730 | 1.796 | +43.5% |
| 삼각 깃발 | 최대풍 | 1.978 | 3.439 | 2.690 | 2.696 | +36.3% |

여섯 중앙값 합의 접촉 증가는12.110→15.430초,약+27.4%다.
최적화 전 ON 대비 최신은17.1~22.9% 단축됐지만, 재사용만 대비 병렬 추가 효과는
약3.8% 단축부터3.8% 증가까지 섞였다. 통제 묶음의 경로별3표본 범위는1.5~16.6%이므로
이 작은 차이를 확정된 병렬 가속으로 해석하지 않는다. 단독 유휴 확인만으로 시간 변동이0이 되지는 않는다.

### 실제 접촉 국소 사례

면/엣지8단계, 고속12단계·barrier1,000·8mm 초기 간격. 접촉 쌍은 최대33개인 작은 사례다.

| 사례 | 최적화 전 ON | 재사용만 ON | v4 ON | 전 단계 최적화 전 대비 단축 |
| --- | ---: | ---: | ---: | ---: |
| 면 접근 | 0.08325s | 0.06705s | 0.06677s | 19.8% |
| 엣지 접근 | 0.09206s | 0.07422s | 0.07760s | 15.7% |
| 고속 접근 | 0.14032s | 0.11143s | 0.11257s | 19.8% |

접촉 OFF는 비교하지 않았다. v4만의 추가 병렬화는 면에서0.4% 단축, 엣지4.6% 증가,
고속1.0% 증가이며, 경로별 시간 변동은1.1~13.8%였다. 고밀도 접힘이나 큰 후보 집합의
병렬 효율·전체 궤적 비용은 이 작은 사례로 판정하지 않는다.

## 남은 병목에 대한 측정 근거

직사각형 rest에서 활성 접촉0, AABB 후보15,217개다. CUDA event로 graph 안에20회 연산을
넣고3표본을 잰 v4 요소별 중앙값은 다음과 같다. 서로 독립 측정한 참고값이므로
단순히 더하거나 전체 프레임 시간의 정확한 구성 비율로 환산하지 않는다.

- 접촉 force 평가 묶음1.458ms, 그중 별도 측정한 bounds/BVH refit·후보 질의 묶음1.262ms.
- 전체 경로 검사0.819ms, 후보별 CCD kernel과 큐 초기화만0.084ms.
- 별도 shell force2.452ms, shell HVP0.429ms. 접촉 밖의 FP64 shell/선형 풀이 비용도 남는다.
- GMRES 작업 배열 초기화는 순차467.9µs→병렬105.1µs였다. 이 단일 연산의 비율을
  전체 프레임 가속으로 쓰지 않는다.

이 수치와 비접촉 첫 프레임이라는 조건으로 볼 때, 이번v4가 손댄 접촉 미분/CCD pair 단계만보다
**BVH 후보 질의와 반복 호출, shell 해법 비용을 먼저 살필 근거**가 있다.
정확한 SM 점유율/warp 편차/메모리 stall의 원인 확정은 Nsight 상세 profile이 필요하다.
이 턴에서는 추가 최적화를 구현하거나 v4를 임의로 되돌리지 않았다.

## 검증·환경·재현

- 통제 비교 측정99프레임4,860단계, 실제 동결 비교36프레임2,304단계, 합계135프레임7,164단계가
  모두 기존 승인 기준을 통과했다. 이 분모는 예열을 제외한다. 예열도 통과했으며 장기 연속 궤적은 아니다.
- 초기 상태 반복 동치, 경로 간 상태 허용오차, frame/step/audit graph의 host copy/callback0 확인.
- 새 동결 버전 실행기의 입력/native hash·정책 불일치 거절·유휴 확인 필수 조건4개 단위 검사 통과.
  기존121개 수치 회귀는 직전v4 검증 기록이며 이번 턴에 다시 실행한 것으로 세지 않는다.
- 사용자 유휴 확인에도 시작 전 드라이버 사용률22~26%,SM607MHz/메모리405MHz/약21W가 표시됐다.
  완전한 외부 부하0의 계측 증명과 구분한다. 측정 구간 telemetry305표본에서 SM 중앙값1911MHz,
  온도 최대66°C였다. 부하/클럭의 원인을 특정하거나 성능 변동을 모두 thermal 문제로 단정하지 않는다.
- 원본 명령·보고서·source/hash·telemetry는 [재현 snapshot](idle_v4_checks/README.md)과
  [집계 JSON](idle_v4_checks/summary.json)이 소유한다. 기존 공유 부하 원본은 보존했다.
- R1에 제한 성능 결과를 반영하고 PDF/bundle을 갱신했다. 장기 접촉·proxy 응답 수렴·RTX5070·R1/Gate는 미완료다.

네트워크 fetch·설치·commit·push는 하지 않았다. 다른 작업은 종료하지 않았다.
